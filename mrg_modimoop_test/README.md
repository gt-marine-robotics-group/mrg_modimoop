# Modimoop autonomy bench, milestone 1

This separate `ament_python` package exercises the installed `mrg_modimoop_control/lqr_heading_controller` executable. The controller subscribes to body-frame odometry twist (`nav_msgs/Odometry`, m/s and rad/s), ENU yaw heading (`Float64`, rad), target yaw (`Float64`, rad), and optional body wind (`Vector3`, m/s); it publishes rudder and backwing joint positions (`Float64`, rad) plus debug data. The bench owns the input topics via the controller's existing topic parameters. It does not launch planner, localization, or robot_localization. In simulation it feeds the controller measured Gazebo pose, finite-difference body twist, and anemometer-derived wind, so the loop under test is controller + actuators + vessel dynamics; localization accuracy is outside this milestone.

## Run

From the workspace root:

```bash
colcon build --merge-install --packages-select mrg_modimoop_test mrg_modimoop_control
source install/setup.bash
ros2 run mrg_modimoop_test bench --suite isolated
ros2 run mrg_modimoop_test bench src/mrg_modimoop/mrg_modimoop_test/scenarios/simulation_beam_reach.yaml
```

The command above runs Gazebo without a GUI. To watch the same scenario, use a desktop session with a working `DISPLAY` or `WAYLAND_DISPLAY` and run:

```bash
ros2 run mrg_modimoop_test bench src/mrg_modimoop/mrg_modimoop_test/scenarios/simulation_beam_reach.yaml --gui
```

While a `--gui` run is active, open a second terminal, source the workspace, and use `ros2 topic list --no-daemon` or `ros2 node list --no-daemon`. GUI runs use the caller's `ROS_DOMAIN_ID` (domain 0 if unset), so plain ROS commands in that second terminal see `/clock`, `/bench/input/*`, `/modimoop/cmd/*`, and the sensor bridges. Run these commands **before** the scenario ends; the bench shuts down its nodes afterward. Headless runs use an isolated domain and print `ROS_DOMAIN_ID=N` plus the matching inspection command on startup. Use `--ros-domain-id N` to choose a domain explicitly in either mode. Do not run an exposed GUI bench alongside another stack publishing the same `/modimoop/cmd/*` actuator topics.

GUI runs also use Gazebo's **default transport partition**. In the second terminal, `gz topic -l` works when `GZ_PARTITION` is unset; `env -u GZ_PARTITION gz topic -l` works even if that terminal has a stale exported value. Headless runs retain a unique partition, and the runner prints a `GZ_PARTITION=... gz topic -l` command on startup. Use `--gz-partition NAME` to choose a named partition in either mode. `runtime.json` records the selected partition (null means Gazebo's default). Gazebo topics disappear when the runner shuts down the simulator.

The bench writes `simulation.wind_world_mps` into its generated world's `<wind><linear_velocity>` and publishes the same ENU vector as `gz.msgs.Wind` on `/world/ocean/wind` during the run. Gazebo Harmonic's WindEffects system subscribes there and updates the wind component read by ASV's sail and anemometer plugins. ASV's `/wind` topic is a separate `gz.msgs.Vector3d` override of that component; it has no publisher in this bench, and WindEffects would overwrite such an override on the next update. The bench waits for a WindEffects subscriber and an anemometer message before starting its timed scenario. `anemometer.csv` records apparent wind in the sensor link frame; `wind.csv` records the body-frame true-wind estimate sent to the controller. The sensor is rotated 180° about Z from the hull, so the bench reverses its horizontal axes and adds measured hull velocity. This 2D estimate ignores hull roll, pitch, and sensor-offset rotation. For GUI inspection, use `env -u GZ_PARTITION gz topic -i -t /world/ocean/wind` and `ros2 topic echo /modimoop/anemometer`. These commands must run while the bench is active.

Lyoko's `spawn_world.launch.py` resolves an installed world and starts Gazebo plus a clock bridge; `spawn_robot.launch.py` expands the boat xacro, spawns it, and starts vehicle bridges and a robot state publisher. This bench uses Lyoko's installed `ocean.world` and the Modimoop description and bridge YAML, but launches Gazebo and the spawn command directly to pass a per-run wind-modified world and keep planner/localization outside the controller test boundary. The bench starts its own `/clock` bridge, the description's vehicle bridge, and the actual `mrg_modimoop_control/lqr_heading_controller`. It does not need `robot_state_publisher` for controller inputs because odometry and heading are injected on dedicated `/bench/input/*` topics.

The runner closes the GUI and simulator when the scenario ends. For a remote or CI machine, omit `--gui` and inspect `controller.png`, `trajectory.png`, and `wingsail.png` afterward. The wingsail joint is passive: the simulation description has no position controller for it, and the bench never publishes a wingsail command. `wingsail.csv` records its position relative to the hull. The current repository model can move backward under the default wind and sail trim; the forward-speed assertion reports that as a scenario failure rather than a valid heading-convergence test. Gazebo's wave hydrodynamics plugin has also crashed in one alternate initial orientation; a process crash is reported as infrastructure failure with `gazebo.log` retained.

For the focused southwest-wind test, run `ros2 run mrg_modimoop_test bench src/mrg_modimoop/mrg_modimoop_test/scenarios/simulation_southwest_wind_0deg.yaml` and add `--gui` to watch it. The currently resolved YAML values determine the wind, warmup, and duration; inspect `resolved.yaml` and `ocean_bench.world` in the run directory to confirm them. For a 10 m/s southwest wind, 30 s warmup, and 180 s run without editing YAML, add `--set 'simulation.wind_world_mps=[-7.0710678118654755, -7.0710678118654755, 0.0]' --set warmup_s=30 --set duration_s=180`. The boat starts at ENU yaw 330° and commands 0° (world +x), a wrapped +30° step. The bench holds the starting heading during warmup and applies the target at the evaluation start. A 3600-second wall watchdog covers a slow GUI simulator; it does not extend the evaluation window. In the current world the wave plugin emits frequent "Water patch is too small" errors, and GUI simulation may run much slower than real time.

An individual isolated scenario is run with `ros2 run mrg_modimoop_test bench src/mrg_modimoop/mrg_modimoop_test/scenarios/isolated_wrap.yaml`. Use `--suite all` for all installed scenarios, `--output PATH` for artifacts, and `--set duration_s=3` or `--set thresholds.max_steady_error_deg=15` for overrides. The program returns 0 for pass, 1 for controller assertion failure, and 2 for infrastructure failure or interruption. Headless runs get isolated ROS and Gazebo domains; GUI runs use the caller's ROS domain and Gazebo's default partition for inspection. It terminates only process groups it starts. Run CI by invoking the same commands after the build; the exit code is the gate. `colcon test` covers package-level tests, while these longer scenarios are explicit integration jobs.

Each run writes a unique directory under `bench_results`: `resolved.yaml`, `versions.json`, `runtime.json`, process logs, ROS observations in CSV, `result.json`, `report.md`, `controller.png`, and for simulation `trajectory.png`. CSV keeps the initial bench lightweight and readable. The recorder stores received input/output values and simulator pose; unlike a rosbag, it does not preserve full ROS message metadata. Failure artifacts are retained. The chart labels and report explicitly say when evidence is missing.

## Scenario format

YAML fields are `name`, `description`, `mode` (`isolated` or `simulation`), `duration_s`, `warmup_s`, `startup_timeout_s`, `wall_timeout_s`, `seed`, `initial`, `targets`, `input`, `parameters`, `evaluation`, `thresholds`, and `simulation`. `targets` contains increasing `{at_s, heading_deg}` pairs, beginning at zero. `at_s` is relative to the evaluation start, after warmup. `initial.heading_deg` is ENU yaw; `initial.speed_mps` supplies isolated synthetic odometry. Gazebo spawns at the requested yaw with zero initial velocity; it builds speed during warmup. `input.heading_sequence` can supply isolated heading samples at specified times; `input.stop_at_s` stops state injection to test stale-input handling. `parameters` overrides ROS parameters on the actual controller. The wingsail is passive; `simulation.wingsail_rad` is no longer accepted. Unknown top-level fields and malformed targets fail validation.

To add a controller scenario, copy one YAML file into `scenarios/`, set its target sequence and thresholds, rebuild, then run it individually. `simulation.wind_world_mps` is an ENU vector used to generate a per-run copy of the ocean world; it does not edit the installed world. Add future planner, localization, and mission suites as separate modules and scenario folders in this package. Reuse process ownership, recording, and reporting; add component-specific ROS adapters and metrics. Localization tests must compare estimated pose against this Gazebo pose, never against an input derived from the estimate.

## Frames, measures, and operating assumptions

Gazebo world `ocean` uses ENU. The pose adapter subscribes with Gazebo's Python transport binding to the existing `/world/ocean/pose/info` Pose_V stream and selects the named model `none_mrg_modimoop`. This avoids the installed ROS/Gazebo bridge's empty frame IDs for that topic. Ground truth is world-frame model position (east x, north y, meters) and quaternion yaw (radians, positive counterclockwise from east). The localization node also derives heading from quaternion yaw and wraps to `[0, 2π)`; the controller wraps to `[-π, π]`. The bench compares `remainder(target - yaw, 2π)`, in degrees. It uses simulator message stamps and `/clock` in simulation; isolated samples use a monotonic wall clock. There is no comparison across these two clocks. Body twist in simulation is computed from consecutive world poses rotated into the hull frame. Commands have their controller parameter sign conventions: `rudder_sign=-1`, `backwing_sign=1`, matching the existing controller YAML; physical turn direction is not asserted without vessel motion.

Steady-state error is mean absolute wrapped heading error over the last configured `steady_window_s`, after the last target. Settling time is the first instant after the last target at which error stays within `settling_band_deg` for `settling_dwell_s`; it is absent when no such interval is observed. Overshoot for a single step is the maximum error beyond the target on the opposite side of the initial error. Actuator violations count finite samples exceeding configured absolute limits; saturation duration sums intervals beginning within 0.01 rad of the limit. Missing or nonfinite outputs fail explicitly. Stale-input scenarios assert safe zero commands after the configured grace period. Metrics with insufficient samples are marked incomplete and fail.

The simulation scenario starts at yaw 90° with a 6 m/s east wind, a beam-reach orientation, and requests 105°. It assumes the boat develops steerage during the 8 s warmup; the bench does not inject initial velocity. The initial 20° steady-error limit is deliberately broad because this is a short 25 s maneuver in a nonlinear sailboat model, but it still requires the vessel to remain near the requested heading. It is a simulation claim only. If speed is insufficient or the controller cannot hold the heading, retain the failure and inspect trajectory/actuator logs rather than weakening the threshold. Gazebo world wind effects include noise and oscillation; seed is recorded but those plugins do not expose a deterministic seed here. Physics scheduling, ROS delivery, and wall-clock launch order are additional nondeterminism sources.

## Approach

The simulation scenario also requires at least 0.1 m/s mean ground speed, 0.1 m/s mean forward body speed, and a 3° reduction in mean absolute heading error from the first 2 s to the final 5 s. These conditions rule out a stationary boat, a boat moving backward, or one that merely stays within a broad heading band. An assertion failure is a finding about this controller in this simulated setup, not an infrastructure error.

`launch_testing` is suitable for compact ROS integration assertions and is available in Jazzy, but this milestone needs parameterized multi-second scenarios, CSV evidence, charts, and explicit simulator watchdogs. The repository's current tests are lint-only and do not provide that lifecycle. The dedicated runner uses installed ROS tools and a small rclpy observer, keeping all simulation/test dependencies outside `mrg_modimoop_control`. A future CI wrapper can call it from a `launch_testing` test if desired. The Gazebo adapter uses the existing world pose stream directly; the [ROS/Gazebo bridge](https://github.com/gazebosim/ros_gz/tree/ros2/ros_gz_bridge) supplies `/clock` and actuator command bridges. No perfect sensor is added to production code.
